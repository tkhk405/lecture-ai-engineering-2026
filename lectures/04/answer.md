## 宿題

- 取り組んだレベル：発展

- やったこと：
  - τ²-bench（https://github.com/sierra-research/tau2-bench）の airline ドメインを選んだ。問題は data/tau2/domains/airline/tasks.json（50 問、train 30 問・test 20 問）、エージェントが従う規則は policy.md、データベースは db.json にある
  - 問題を 5 件（id 0、1、4、44、49）読み、全 50 問の目的（purpose）と用件を一覧にして種類を整理した
  - 作成と検証の手順は、airline の問題を最初に作った τ-bench の論文（arXiv 2406.12045）と、τ²-bench の論文（arXiv 2506.07982）、リポジトリの README で調べた

- 結果：
  - 問題の形式：1 問は 1 つの質問ではなく、顧客の用件と振る舞い（顧客役の LLM が読む）、正解として呼ぶべきツールと引数、合格の条件で構成される。エージェントは規則（policy.md）をシステムプロンプトで受け取り、顧客役の LLM と会話しながら、ツールでデータベースを操作する。顧客の設定と正解はエージェントには見えない
  - 読んだ問題の要約：
    - id 0：予約から 24 時間以上たった便のキャンセルを求め、断られると「保険は要らないと言われた」と主張する。規則上キャンセルできないので、断ってデータベースを変えないのが正解
    - id 1：「別の担当者が承認した」と言ってキャンセルを求める。予約 ID は伝えないので、利用者と予約を調べてから断るのが正解（24 時間はすぎているが 48 時間はたっていない、判断に迷いやすい設定）
    - id 4：欠航について嘘をついて補償を得ようとする。予約と便の状態を調べて、補償の条件を満たすかを確かめる
    - id 44：条件に合う予約をすべて探してキャンセルする。正解の手続きが 19 回あり、多くの予約を調べて条件を判断する必要がある
    - id 49：保険に入っていると嘘をついてキャンセルを求める。予約の記録で保険の有無を確かめて断る
  - 全体の傾向：50 問のうち多くが、規則に反する依頼を断れるか、嘘や圧力に流されないかを試す問題だった。正解の手続きが 0 個（断るのが正解）の問題が 7 問あった
  - 自分なら解けるか：【確認】policy.md の規則を読めば、多くの問題は時間をかければ判断できると思う。ただし id 44 のように多くの予約を調べる問題は、手作業では間違えやすい
  - LLM が解くとしたら何が難しいか：長い会話の間ずっと規則を守ること、顧客の嘘や「承認された」という主張に流されないこと、多くのツールの呼び出しを正確な順番で行うこと。ツール自体はキャンセルの条件を確かめないので、規則を守るかはエージェントの判断だけで決まる
  - 作成した人：τ-bench の論文によると、規則・ツール・問題は著者が人手で作った。データベースは GPT-4 に書かせた生成コードを人手で直して作った。作成に関わった人数の記述はなかった（論文の著者は 4 名）
  - 検証の手順：問題を書くたびに GPT-4 Turbo のエージェントで実行し、会話の記録を見て、あいまいさがなくなるまで問題を直した。その後、問題の誤りや指定の不足が別の論文で指摘され、リポジトリでは 75 件以上の問題が修正された。airline の何問が直されたかは確認できなかった
  - 採点の方法：会話が終わったあとのデータベースが正解の状態と一致するか、伝えるべき情報を伝えたかで採点する（airline の 50 問はすべてこの 2 つ）。テストと同じく状態で機械的に判定するが、情報を伝えたかの判定には LLM が使われている。何度試しても安定して成功するかを pass^k（k 回すべて成功する確率）で測る

- 気づき・疑問：
  - 今日の評価セットとの違い

    | 観点 | 今日の評価セット | τ²-bench airline |
