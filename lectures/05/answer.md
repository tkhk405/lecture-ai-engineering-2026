- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - 用語を入口にする Graph の取得方法を作り、`--term` で起動できるようにした。Graph でページを選び、Tree の情報（章の名前）で渡す量を決める組合せになっている
  - きっかけ：質問1（下記）を基本RAGで実行したところ、「構造化出力」が出てくる12ページのうち、回答が引用したのは第3回の4ページだけだった。第2回 p.53 の「実務で形だけ守らせるなら API の構造化出力が先」という記述に届いていなかった
  - 原因の切り分け：`uv run python -m app.retrieval "第2回 構造化出力"` で検索だけを実行すると、上位5件は第3回 p.34・33・62・35 と第2回 p.60 で、p.53 は入っていなかった。「取れたのに使えなかった」のではなく「取れなかった」。p.53 はページ全体としてはファインチューニングの話で、用語は1文に出るだけなので、ページ単位の埋め込みでは順位が上がらない。また、検索語に「第2回」と入れても回では絞られない
  - 設計
    - データの形：`graph.json` の用語ノード（72語、別名つき）と、ページと用語を結ぶ `mentions` の関係を使う。既存の `search_graph` はベクトル検索の上位を入口にするが、今回は用語ノードそのものを入口にした
    - 検索方法：検索語に用語名か別名が含まれる用語ノードを探し、`mentions` でつながる第1〜3回のページを全件、回・ページの順に返す。ベクトル検索も埋め込みAPIも使わない。件数で打ち切らないので、モデルは「全部で何ページあるか」を知ることができる
    - 渡す内容：ページのタイトルか章の名前に用語があれば、その用語を説明するページとみなして全文を渡す。それ以外（目次・まとめ・主題が別のページ）は、用語を含む文だけを渡す
    - 理由：説明の中心のページ（第3回 p.34）は、見出しに用語があるだけで説明文に用語が出てこないので、用語を含む文だけでは中身が落ちる。逆に第2回 p.53 は、用語を含む1文が欲しい内容そのものだった。12ページの全文は合計6,088文字、この方法では2,135文字になる
  - 変更したファイル

    - `app/tools.py`：モデルが呼ぶツール `search_term`
    - `app/agent.py`：`--term` の切り替え、指示文 `TERM_INSTRUCTIONS`、取得したページの一覧を出す trace の表示
    - `tests/test_term_search.py`：12ページが取れること、第2回 p.53 が入ること、渡す量の切り替えのテスト4件
  - AIツールの利用：コードは Claude Code と一緒に作った。質問の実行、trace の読み取り、原文との照らし合わせは自分のターミナルで行った
